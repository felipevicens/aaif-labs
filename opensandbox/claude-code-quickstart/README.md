# OpenSandbox + Claude Code: lab

Companion scripts for the post **"Let Claude Code Run Anything, Without
Letting It Touch Your Machine"**, the first post about
[OpenSandbox](https://github.com/opensandbox-group/OpenSandbox), an AAIF
project.

OpenSandbox runs a small server on your machine that creates throwaway Docker
containers ("sandboxes") on demand, and lets you run commands and move files
inside them through an API, a CLI (`osb`), SDKs and an MCP server. The lab
uses it three ways:

1. **By hand** with `osb`: create a sandbox, run commands, install a package,
   kill it. No model, no key.
2. **From Claude Code over MCP**: Claude Code tests a repo you don't trust,
   but every command runs in a sandbox, never on your machine.
3. **Claude Code inside a sandbox, in YOLO mode**
   (`--dangerously-skip-permissions`), with a deny-by-default network policy
   and Credential Vault, so the agent never sees your real API key.

## Layout

```
00-install-and-run.md        # exact commands, run order, cleanup
scripts/
  setup.sh                   # installs OpenSandbox 1.2.0, writes ~/.sandbox.toml, starts the server
  01-first-sandbox.sh        # Scenario 1: osb by hand (no key)
  02-mcp-add.sh              # Scenario 2: register the MCP server in Claude Code
  03-yolo-with-vault.py      # Scenario 3: Claude Code in a sandbox + network policy + Credential Vault
  teardown.sh                # kills sandboxes, stops the server, removes the MCP entry and the tools
```

## Tested with

- Ubuntu 24.04.3, kernel 6.8, **Docker Engine 29.9.2** (from docker.com), `uv` 0.12.5
- OpenSandbox **1.2.0**: `opensandbox-server`, `opensandbox-cli`, `opensandbox-mcp`,
  Python SDK `opensandbox`, images `opensandbox/execd:release-1.2.0` and
  `opensandbox/egress:release-1.2.0`
- Claude Code **2.1.316**
- Sandbox images: `python:3.12-slim`, `python:3.12`, `node:22-bookworm`

The whole lab was run twice from zero (teardown with `--purge`, images removed)
on a clean host, including the failure paths described in the post.

## Keys

- Scenario 1 needs no key at all.
- Scenarios 2 and 3 need a model key for Claude Code: `ANTHROPIC_API_KEY`, or
  `ANTHROPIC_AUTH_TOKEN` plus `ANTHROPIC_BASE_URL` if you go through your own
  Anthropic-compatible gateway. `03-yolo-with-vault.py` handles both.
- The OpenSandbox server's own `api_key` is generated by `setup.sh` and lives
  in `~/.sandbox.toml`. Nothing in this folder contains a key.

## Known environment trap

**Docker from snap (Ubuntu) can't run OpenSandbox sandboxes.** OpenSandbox
starts every sandbox with `no-new-privileges`, which is the safe default.
Docker's snap package runs under the AppArmor profile `snap.docker.dockerd`,
and the kernel then denies the exec inside the container:

```
exec /opt/opensandbox/bootstrap.sh: operation not permitted
apparmor="DENIED" operation="exec" info="no new privs" profile="snap.docker.dockerd"
```

Any `docker run --security-opt no-new-privileges=true` fails the same way on
that Docker, so it's not an OpenSandbox bug. Install Docker Engine from
[docs.docker.com/engine/install/ubuntu](https://docs.docker.com/engine/install/ubuntu/)
instead. Turning `no_new_privileges` off in `~/.sandbox.toml` also "works", but
it weakens the isolation the whole lab is about.
